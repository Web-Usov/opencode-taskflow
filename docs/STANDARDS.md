# Стандарты проекта и подготовка требований

Этот слой отвечает на вопросы «какие правила относятся к работе?» и «достаточно ли ясны требования?». Управление задачами, worktree, проверками и PR остаётся за Taskflow. Agent OS устанавливать не нужно.

## Один источник правды

Правило остаётся в исходном документе: `AGENTS.md`, спецификации, ADR или руководстве проекта. Индекс хранит ссылку, описание области применения и статус. Он не заменяет исходный документ и не повышает наблюдение из кода до обязательного правила.

Например, можно сослаться на уже существующую спецификацию ошибок API:

```json
{
  "version": 1,
  "entries": [
    {
      "id": "api-errors",
      "title": "Контракт ошибок API",
      "description": "Формат ответа, коды ошибок и проверки отрицательных сценариев",
      "path": "docs/spec/errors.md",
      "areas": ["api"],
      "tags": ["errors", "validation"],
      "status": "draft"
    }
  ]
}
```

Это пример структуры, не готовое правило для любого проекта. Файл по ссылке должен существовать. Несколько записей могут ссылаться на один документ; его содержимое загружается один раз. Точные ID бизнес-правил продолжайте указывать в `spec` и тестах.

## Как формируются стандарты

`/tf-discover api` просит агента:

- сначала прочитать действующие требования и ограничения;
- найти характерные фрагменты кода и тесты, а также исключения;
- отделить наблюдение от рекомендации, спросить о причинах выбора;
- представить предложения человеку на настроенном языке.

Повторяющийся код может быть техническим долгом. Частота паттерна не означает правильность. Изменения оформляет planner на ветке `plan/<slug>` после явного подтверждения человека. Новое предложение остаётся `draft`, пока человек его явно не одобрит. Изменения индекса, `docs/standards/**` и `docs/plans/**` требуют человеческого слияния согласно процессу.

Поле `approved` не защищено криптографически: это подсказка маршрутизации, а не проверенная системой подпись человека. Ограничения shell-команд и роли не заменяют защиту веток GitHub.

## Как выбрать правила для задачи

Инструмент `tf_standards` доступен для чтения:

```json
{ "operation": "list" }
```

```json
{ "operation": "suggest", "area": "api", "tags": ["validation"], "query": "обработка ошибок" }
```

```json
{ "operation": "load", "ids": ["api-errors"] }
```

```json
{ "operation": "check" }
```

Подсказки основаны на метаданных индекса и не подгружают содержимое всех документов. Они не выбирают и не одобряют правила. Planner записывает точный список подтверждённых стандартов в необязательное поле задачи:

```yaml
standards: [api-errors]
```

Старые задачи без поля и задачи со `standards: []` не требуют индекса. Черновики доступны только явно через `includeDrafts: true` для обсуждения человеком/planner; implementer, reviewer и qa не могут загрузить их этим инструментом.

При `tf_dispatch` с указанной задачей исполнитель и ревьюер получают один и тот же набор явно выбранных источников из worktree задачи. В отчёте есть ID, путь и SHA-256. Неизвестные, повторяющиеся и черновые ID, опасный путь или слишком большой контекст дают ошибку до создания дочерней сессии.

Источники перечитываются на каждом запуске: постоянного снимка между реализацией и ревью нет. Если SHA-256 изменился, это нужно учитывать при ревью; одинаковая привязка ID не гарантирует неизменность файла во времени. В ручном режиме роли обязаны загрузить точные ID до работы; подсказки в промпте не являются технической гарантией этого действия.

При продолжении дочерней сессии через `sessionID` Taskflow восстанавливает её исходную задачу из метаданных сессии и снова проверяет выбранные правила до отправки промпта. Нельзя незаметно заменить задачу, роль, родительскую сессию или каталог. Для старой сессии, чью привязку нельзя восстановить, потребуется новый дочерний запуск — отсутствие `task` не сбрасывает проверку.

## Как уточнить требования

`/tf-shape <функция>` создаёт работу для planner в отдельном worktree. Результат — `docs/plans/<slug>/shape.md` на языке человека:

- цель и не-цели;
- примеры и крайние случаи;
- критерии приёмки и способ проверки;
- ссылки на похожий код, макеты, действующие требования и стандарты;
- открытые вопросы и явное состояние подтверждения человеком.

Отсутствие ответа не означает согласия. Пока блокирующие вопросы не решены, planner не раскладывает неоднозначные требования в задачи реализации. `/tf-plan` использует уже подтверждённые материалы, не заставляя заново проводить интервью для понятной маленькой задачи. Shape-документ не может молча изменить спецификацию или ADR.

## Настройка и ограничения чтения

```jsonc
{
  "standards": {
    "index": "docs/standards/index.json",
    "roots": ["docs", "AGENTS.md"],
    "maxContextChars": 24000
  }
}
```

Пути относительные, внутри репозитория и разрешённых корней. Для собственного расположения индекса добавьте его каталог в `roots`. Разрешены текстовые источники `.md`, `.txt`, `.rst`, `.adoc`.

Переходы `..`, абсолютные/сетевые пути, скрытые файлы, `node_modules`, пути секретов, игнорируемые Git файлы и symlink за пределы разрешённой области запрещены. Это проверка пути и типа источника, не поиск секретов в тексте: нельзя хранить ключи в разрешённой документации. Все загруженные материалы подчинены `AGENTS.md`, спецификации, ADR и ограничениям прав.

Бюджет включает заголовки и содержимое. Превышение — ошибка без частичного результата и обрезки. Если источник слишком велик, разделите его в каноническом месте, а не создавайте расходящуюся копию специально для индекса.
